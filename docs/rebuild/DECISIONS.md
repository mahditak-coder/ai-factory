# Architectural Decisions

Numbered decisions for the rebuild. Status may be ACCEPTED, PROPOSED or UNRESOLVED. Unresolved decisions must not be silently made during a phase.

- **ADR-001 — Single canonical orchestrator state machine** — ACCEPTED. Rationale: duplicated execution paths and stale state caused drift. Alternatives: keep legacy paths. Consequence: Phase 01 must migrate state with idempotency.
- **ADR-002 — Delegation over self-reference in ModelGateway seam** — ACCEPTED. Rationale: `oc_state()` recursion is P0. Consequence: production test must not mock the seam.
- **ADR-003 — One specialist catalog** — ACCEPTED. Rationale: ROLES/EXTRA_ROLES/agents/workflow DAG drift. Consequence: aliases retained, no duplicate registries.
- **ADR-004 — Dynamic activation, not all agents always** — ACCEPTED. Rationale: quality and cost. Consequence: activation matrix required in Phase 05.
- **ADR-005 — Independent Critic for high-impact acceptance** — ACCEPTED. Rationale: producer cannot be sole authority. Consequence: Phase 07.
- **ADR-006 — Evidence-bound quality decisions** — ACCEPTED. Rationale: report writing is not gate passing. Consequence: Phase 08.
- **ADR-007 — Severity-first release gate** — ACCEPTED. Rationale: score cannot hide Critical. Consequence: Phase 09.
- **ADR-008 — Product domain independent of delivery platform** — ACCEPTED. Rationale: game may target Android/Web/Desktop. Consequence: Phase 02/05.
- **ADR-009 — Environment-only credentials** — ACCEPTED. Rationale: public repository safety. Consequence: no config secrets ever.
- **ADR-010 — No fake PASS** — ACCEPTED. Rationale: audit requirement. Consequence: PASS/FAIL/NOT TESTED evidence rules.
- **ADR-011 — Target game engine and 3D scope** — UNRESOLVED. Options: Android-first 2D/2.5D toolchain, Godot/Unity later with capability proof. Must be resolved with user before Phase 06 production decisions.
- **ADR-012 — Paid image/audio providers** — UNRESOLVED. Options: remain free-model-first, or add verified paid providers with explicit cost approval. Must not be assumed.
- **ADR-013 — Browser screenshot tool policy** — UNRESOLVED. Options: add narrowly scoped approved screenshot tool, or accept visual QA NOT TESTED. SecurityPolicy must not be bypassed.
- **ADR-014 — Checksum repair ownership** — PROPOSED. Repair as separate audit-maintenance change, never silently inside product phase.
- **ADR-015 — Canonical event envelope** — ACCEPTED (Phase 01). ToolEvent and AgentEvent use one schema-versioned envelope with event_uid and seq; legacy keys preserved for SSE/Workspace compatibility.
- **ADR-016 — Durable replay receipts** — ACCEPTED (Phase 01). A repeated `call_id` is rejected and never re-executes; the in-memory ledger no longer clears itself. Rationale: idempotency must survive restarts.
- **ADR-017 — Lease-based stale RUNNING recovery** — ACCEPTED (Phase 01). A RUNNING stage with a dead run_pid is reopened as REVISION with history; no artifact, version or approval is deleted. Rationale: crash recovery without data loss.
- **ADR-018 — Observable cancellation** — ACCEPTED (Phase 01). Cancellation requests are durably recorded and queryable; cooperative adapters may acknowledge, but a non-cooperative worker is never assumed stopped. Force-killing threads is out of scope.
- **ADR-019 — Test isolation assertion generalized** — ACCEPTED (Phase 01). Removed a hardcoded temp path prefix that made `test_root_isolated_when_env_set` fail in valid isolated roots; no product behavior changed.
- **ADR-020 — One canonical versioned request model with deterministic intelligence** — ACCEPTED (Phase 02). Rationale: competing request registries and guessed intent caused over-asking and unsafe routing. Consequence: `core/request_intelligence.py` is the only intake source of truth; Persian/mixed classification is deterministic and explainable, with no provider dependency and a deterministic fallback. Model-assisted classification is not part of Phase 02 and is not claimed.
- **ADR-021 — Domain/platform separation and bound approval** — ACCEPTED (Phase 02). Rationale: ADR-008 requires game≠Android and Android≠game; stale approvals are unsafe. Consequence: separate validated fields/functions for domain and platform; approval bound to request ID, revision, request hash, plan hash, scope, named actor and one-shot expiring token, with fail-closed replay/invalidation. ADR-011..014 remain untouched and unresolved.
- **ADR-022 — Evidence-graded research and versioned Product Brief** — ACCEPTED (Phase 03). Rationale: unverified external claims and overwritten briefs made product decisions unauditable. Consequence: `core/research_product.py` records source provenance and claim grades (`verified_fact`/`hypothesis`/`estimate`/`unknown`), blocks auto-selection without evidence, keeps immutable prior brief versions, binds final scope/success approval to an explicit user token, and performs no paid/specialist/provider execution in Phase 03. ADR-011..014 remain unresolved and untouched.
- **ADR-023 — Verification truth and atomic product approval** — ACCEPTED (Phase 03 repair). Rationale: a caller-declared claim label cannot create evidence, and a brief approval checked outside the lock could attach to a revised version. Consequence: `claimed_type` is declaration only; `verification_status` is system-controlled and remains `unverified` without a trusted verifier; `.invalid`/unchecked sources never count as sufficient; auto-selection fails closed; brief approval re-reads and validates the current record, consumes the token, and writes inside one canonical lock; artifact paths are allowlisted/containment-checked before any side effect; option scores are utility scores (higher = more desirable, never raw amounts). ADR-011..014 remain unresolved and untouched.
- **ADR-024 — One canonical specialist registry with enforced contracts** — PROPOSED / AWAITING INDEPENDENT ACCEPTANCE (Phase 04; not accepted). Rationale: `ROLES`, `EXTRA_ROLES`, `agents/*.json` and workflow DAGs drifted; prompt-only scopes and stale PASS results were unsafe. Consequence: `core/specialist_engine.py` is the single validated registry (24 IDs + legacy aliases); permissions come from contracts; handoff uses full text with current SHA-256 revalidation; stale run tokens cannot produce PASS; final responses require a complete assistant turn; legacy mode is an explicit flag with no automatic fallback. ADR-011..014 remain unresolved and untouched; no domain teams, critic loop or release system were implemented.
- **ADR-025 — Domain team activation matrix** — PROPOSED / AWAITING INDEPENDENT ACCEPTANCE (Phase 05). Rationale: Phase 04 provided one canonical catalog but no domain-aware activation, which risked activating unnecessary or duplicated specialists. Consequence: `core/domain_teams.py` selects roles deterministically from product domain, delivery platform, goal capabilities, constraints, dependencies and risk, using ONLY the Phase 04 canonical registry; capability-only domain roles are additive contracts; per-domain feature flags fall back to the accepted Phase 04 read-only composition; no specialist execution, provider, media or release authority is added. ADR-011..014 and ADR-024 are unchanged.
